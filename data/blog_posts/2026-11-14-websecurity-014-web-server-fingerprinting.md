## 1. Introduction

Web server fingerprinting identifies clues about the software handling HTTP requests. It helps confirm an inventory, locate an unexpected deployment, and select follow-up checks. It maps to **WSTG-v42-INFO-02**.

Fingerprinting produces evidence with different confidence levels. A banner is a claim in a response; an authoritative package inventory is direct evidence of installed software. Keep that distinction throughout the assessment.

## 2. Fundamentals

### Responses provide clues

Observations include `Server` headers, default error-page formatting, redirect behavior, cookie conventions, and protocol characteristics. One clue may suggest a software family without reliably identifying its version.

Formatting and header ordering change across versions and intermediaries. A tool's confidence label should come with an explanation of which observations support its conclusion.

### The visible server may be an intermediary

A CDN, gateway, WAF, or load balancer can generate responses or rewrite backend headers. A 403 may come from an edge component while a 200 comes from the application. Preserve the endpoint, status, and request path with each clue.

Different routes can reach different backends. Sampling the homepage does not establish the software used for every upload service, API version, or administrative interface.

### Identification is different from vulnerability validation

An accurate product name does not establish that a specific advisory applies. Backported fixes, disabled features, and build options can affect applicability. Confirm installed components and configuration through deployment records or the system owner's inventory.

### Separate three technology layers

The HTTP server, application framework, and application product are different identification targets. Nginx may proxy a Node application using a particular framework, while a CDN terminates the public TLS connection. A clue about one layer does not establish the versions of the others.

For example, a cookie name can suggest an application framework without identifying the edge server. A familiar HTML page can be a copied template. A path ending in `.php` can be routed arbitrarily. Protocol support visible to the browser usually describes the public terminator, which may speak a different protocol to the origin.

Record which layer each observation plausibly describes. This reduces false conclusions when headers, body templates, and deployment records appear inconsistent.

### Use a confidence ladder

| Evidence | Reasonable conclusion | Remaining uncertainty |
| --- | --- | --- |
| Single advertised banner | The response claims a product or version | It may be synthetic, stale, or rewritten |
| Several consistent response traits | A software family is plausible | Traits may be shared or generated by a proxy |
| Owner-provided deployed image and package record | A specific component is installed | The relevant feature and exposure still need review |
| Advisory-matched configuration and bounded verification | A particular weakness applies to the assessed path | Other environments or paths may differ |

Confidence in identity and confidence in vulnerability applicability are separate. A completely accurate product fingerprint can still lead to a non-applicable advisory if its vulnerable module is not installed or its affected feature is absent.

### Collect representative responses deliberately

Select a normal page, a representative API response, an ordinary missing path, and a documented authentication response where permitted. Preserve the method and host as well as the path. HEAD and GET can pass through different handlers, and error responses can be generated by a different layer from successful responses.

Do not provoke crashes merely to obtain an error template. A normal missing route is often enough to inspect default behavior. If stronger testing is required later, it should be driven by a specific assessment objective rather than an attempt to collect more fingerprints.

## 3. Vulnerability

Verbose banners and default pages can reveal unnecessary implementation details. That may aid discovery, but removing a banner does not repair an outdated server or unsafe configuration.

Another failure occurs when a misleading fingerprint becomes a supposedly verified vulnerability. Reports can recommend the wrong patch, overlook a different component, or misidentify the exposed layer.

### Explain contradictory fingerprints before escalating

Suppose one route advertises Nginx, another produces a framework-branded error page, and a third returns a CDN challenge. These observations can all be consistent with one deployment: different layers generated different responses. Do not force them into a single product/version field and lose their provenance.

Other response differences can come from content negotiation, compression, cache hits, regional routing, authentication state, or a protection layer selecting a challenge response. Preserve the request headers and session context needed to reproduce the observation. Avoid assuming that a different-looking page means a different vulnerable server.

TLS information needs similar care. A certificate issuer identifies the certificate's trust relationship, not the application-server product. Public ALPN negotiation describes the protocol selected on that connection; it does not prove the origin backend uses the same protocol. A CDN hostname in a response can identify an intermediary without establishing how the private backend is implemented.

Use an observation table when clues disagree:

| Observation | Candidate explanation | Confirmation needed |
| --- | --- | --- |
| Header appears only on successful requests | Application handler or route-specific upstream sets it | Route and proxy configuration |
| Branded denial page differs from normal JSON | Edge protection generated the response | Gateway logs or documented rule behavior |
| Version string differs from package inventory | Rewrite, stale template, or different instance | Deployed image and request-to-instance correlation |
| HTTP/2 visible publicly, HTTP/1.1 in application logs | Proxy translates protocols | Edge and upstream connection configuration |

The right outcome may remain "unconfirmed" until the owner supplies evidence. That is more useful than an overconfident product guess because it identifies the precise next investigation step and prevents unnecessary version-specific testing.

## 4. Attack scenario

A default error page displays an old server version. A tester reports every advisory matching that version without further checks. The deployment actually runs a maintained build behind a proxy retaining an outdated banner template.

Confirm the actual package and affected feature before claiming exploitability. The default page may still deserve cleanup, but its evidence supports an information-disclosure observation rather than every possible version-specific vulnerability.

## 5. Technical demonstration

Run the [local lab](/assets/websecurity/websecurity-lab.mjs) with `node websecurity-lab.mjs`, then inspect two paths:

```sh
curl.exe -i http://127.0.0.1:8080/fingerprint
curl.exe -i http://127.0.0.1:8080/not-present
```

Use `curl` on systems without `curl.exe`. The first response includes a fabricated `Server: ExampleServer/0.0 (synthetic)` header. The application actually runs on the Node runtime you started. A header therefore cannot prove which product is installed.

The missing path returns a plain 404 without that fabricated banner. Compare status, content type, body, and headers. Differences can reflect routing or handler behavior rather than different products.

Record the result with uncertainty:

```yaml
endpoint: http://127.0.0.1:8080/fingerprint
observation: synthetic ExampleServer header
inference: response advertises a product name
confidence_in_installed_product: unverified from HTTP alone
confirmation: inspect local script and runtime inventory
```

This exercise uses ordinary low-volume requests. Aggressive malformed-request probing is unnecessary to demonstrate the distinction between observed responses and confirmed component identity.

### Collect observations with a small local script

Save this as `fingerprint-observations.mjs` while the lab is running:

```js
const base = "http://127.0.0.1:8080";
const probes = [
  { method: "GET", path: "/fingerprint" },
  { method: "HEAD", path: "/fingerprint" },
  { method: "GET", path: "/not-present" },
];

const observations = [];
for (const probe of probes) {
  const response = await fetch(base + probe.path, { method: probe.method });
  observations.push({
    method: probe.method,
    path: probe.path,
    status: response.status,
    advertisedServer: response.headers.get("server"),
    contentType: response.headers.get("content-type"),
    bodyPreview: (await response.text()).slice(0, 80),
  });
}
console.table(observations);
```

Run `node fingerprint-observations.mjs`. Expect the fabricated banner on both `/fingerprint` responses, an empty HEAD body, and a 404 with no Server header for the missing path. Nothing about the absent header establishes that a different HTTP server handled the 404; in this lab, the source proves all three responses came from the same Node process.

The body preview is appropriate only because these are known synthetic fixtures. A production collection script should minimize or redact private response content and respect its approved request set.

### Walk from observation to a defensible report

First preserve the raw observation: "GET on this route advertises this header." Next state the inference and confidence: "the response suggests this software family, unconfirmed." Then ask the owner for deployed package or image evidence and determine which component generated the response.

Only after confirming the component should you compare it with a vendor advisory. Check affected features, version ranges, distribution patches, and configuration preconditions. If a bounded verification is appropriate, use synthetic inputs in the approved environment and record the result separately from the initial fingerprint.

If confirmation is unavailable, report the uncertainty instead of converting a tool label into a fact. "Version disclosure requiring inventory confirmation" and "confirmed remotely reachable vulnerability" need different remediation language and impact claims.

### A misleading version can fail in both directions

An old-looking banner may come from a patched distribution that backports fixes. A new-looking banner may be manually configured while the underlying binary remains old. Therefore, neither an alarming string nor a reassuring string establishes patch state. Use image digest, package release metadata, and running-deployment evidence to resolve the question.

## 6. Impact

Accurate fingerprints help prioritize configuration and patch review. Unnecessary details can reduce discovery effort for an attacker, while false certainty wastes remediation work. Assess confirmed weaknesses through their reachable behavior and affected assets.

## 7. Prevention

Maintain server packages and deployment images, remove default applications, and minimize unnecessary version disclosure. Keep an authoritative inventory. Harden both edge and backend layers so a cleaned-up public banner does not hide an unmaintained service.

### Minimize disclosure with product-specific controls

For an Nginx reverse proxy, these directives illustrate two separate disclosure controls within a suitable HTTP configuration context:

```nginx
server_tokens off;
proxy_hide_header X-Powered-By;
```

`server_tokens off` suppresses Nginx version detail in relevant headers and generated pages; it does not promise to erase every indication that Nginx is present. `proxy_hide_header` prevents a selected upstream header from being passed through. Confirm behavior against the deployed Nginx version and surrounding configuration.

The application may still expose stack traces or technology details in its own body, and the CDN may add independent headers. Review each layer rather than adding many cosmetic rewrites in one place. Patch state, secure configuration, and restricted administrative exposure remain the controls that address the underlying operational risk.

## 8. Detection and testing

Collect representative responses and label their generating component where known. Compare observations with manifests and package records. For a suspected advisory, verify the affected feature and fixed build using primary vendor guidance before assigning impact.

### Verify changes across the actual response paths

After changing disclosure settings, compare ordinary success, redirect, authentication-denial, and missing-route responses. Use approved error fixtures for deeper error behavior instead of triggering unplanned failures. Check both direct application responses and the public edge, using access arrangements approved by the service owner.

Also verify that the fix did not break debugging. Removing public version strings should not remove internal build identifiers and deployment records that operators need. Good hardening reduces unnecessary external information while preserving authoritative internal observability.

## 9. Checklist

- [ ] Separate raw observations from product guesses.
- [ ] Identify intermediaries that can rewrite responses.
- [ ] Compare representative paths and status codes.
- [ ] Confirm software and patch state through inventory.
- [ ] Remove unnecessary banners and default pages.
- [ ] Validate advisory applicability before reporting a vulnerability.
